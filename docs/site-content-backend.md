# Site content backend notes

The CMS stores editor state in `public.site_content_entries.draft_data`. Public reads never use that table: they query only `public.site_content_publications`, whose rows are updated in the same transaction as explicit Publish, removed on Archive/Unpublish, and filtered by the database publication window. Saving a published record increments its editor revision while retaining its published status and its previous public snapshot; the editor flags unpublished changes by comparing revisions. Restore turns an archived record into a private draft, not a publication. The compare-and-swap update RPC checks the submitted revision and updates the editor row, snapshot, and audit record atomically.

`POST /api/site-admin/seed` is the only import path. It inserts the committed seed by stable `seed_key` and never updates an existing row. It is not called at startup. The seed uses `teamMembers` as the one member/alumni source, the installed track definitions for track and committee mission text, and only the comments-marked verified sponsor registry. In the unconfigured preview, verified canonical member names and roles are visible with shared committee mission explicitly labeled, not claimed as individual responsibilities. CMS member imports remain private drafts until the owner supplies at least one actual individual responsibility. Omar Mehawed is excluded from public fallback; unresolved leadership placeholders are not public entries. Existing source events remain drafts for owner review. Any imported record that fails publish readiness is downgraded to draft.

The migration keeps editor rows, audit records, and inquiries inaccessible to `anon` and `authenticated`. The publication table grants only selected content columns to public roles under an RLS time-window policy. The Storage bucket is public-read for published media URLs but browser writes are denied except for an owner-only policy; upload APIs use server credentials only after the existing database-verified owner/password-lifecycle guard. If the bucket or schema is missing, the upload API returns 503 rather than claiming success.

`POST /api/site-contact` validates bounded plain-text fields, rejects a non-empty honeypot, and rate-limits by request IP (Upstash when configured, otherwise bounded per-process fallback). It inserts into `site_inquiries` using the server client and replies that the inquiry was **stored**, not emailed. Missing service configuration or schema produces 503, not a simulated sent message. The endpoint does not send email because no approved email delivery contract was assigned to this backend.
